### 4. Logging and Diagnostics

Use this standard to control, format, and filter diagnostic logs across application layers, ensuring minimal runtime overhead and clean terminal output.

---

#### 1. Verbosity Levels and Use Cases

| Macro | Log Level | Target Audience | Intended Use Case |
| :--- | :--- | :--- | :--- |
| **`SYS_LOG_E(...)`** | **ERROR** | Operator / Developer | Critical execution failures (e.g., failed heap allocations, driver initialization errors, or transaction failures that abort a process). |
| **`SYS_LOG_W(...)`** | **WARN** | Operator / Developer | Recoverable anomalies, unusual system states, or redundant API calls (e.g., trying to stop a server that is already stopped, or identical OTA firmware detected). |
| **`SYS_LOG_I(...)`** | **INFO** | End User / Operator | Major system lifecycle events and state transitions (e.g., interface successfully initialized, server started, or URI successfully registered). |
| **`SYS_LOG_D(...)`** | **DEBUG** | Developer | High-frequency diagnostics, payload dumps, and low-level state transitions. |

---

#### 2. Debug Filtering and Compilation Flags
To prevent high-frequency debug logs from consuming flash space or CPU cycles in production, compile-time stripping must be controlled on a per-module basis.

*   **Rule:** Debug logging (`SYS_LOG_D`) is stripped by default. To enable it for a specific `.cpp` file, define the local enablement macro **prior** to including the log handler header.
*   **Module Placement Template:**
    ```cpp
    #include "mem_ota.hpp"
    #include "esp_image_format.h"

    // Enable debug logging for this specific module only
    #define ENABLE_SYS_LOG_D
    #include "System/LogHandler.h"
    #include "System/errorTranslateHandler.h"
    ```

---

#### 3. Performance and Formatting Rules

*   **Avoid Unnecessary String Concatenations:** Do not use `std::string` concatenation (using `+` or `std::to_string()`) within `SYS_LOG_D` blocks unless debug logging is explicitly enabled. If debug logging is disabled, the string concatenation will still execute on the CPU at runtime, causing silent performance loss.
*   **Standard C-Style Formatting:** Use standard printf-style format specifiers and PRI macros for platform portability (e.g., `PRIx32`).
*   **ISR Context Logging:** Never call standard `SYS_LOG_x` macros inside an Interrupt Service Routine (ISR) context. Standard logging is blocking and relies on thread-unsafe printf locks.
*   **Formatting Templates:**
    ```cpp
    // BAD: CPU cycles are wasted on string allocation even if DEBUG logs are disabled
    SYS_LOG_D("Socket FD: " + std::to_string(sockfd));

    // GOOD: Zero allocation; optimized away at compile time if DEBUG is disabled
    SYS_LOG_D("Socket FD: %d", sockfd);
    
    // GOOD: Portably formatting hardware addresses/registers
    SYS_LOG_I("Writing to partition subtype %d at offset 0x%" PRIx32, subtype, address);
    ```

---

#### 4. Macro Call Alignment
When error and warning logs are coupled with the error return macros on multiple lines, they must use right-aligned, descriptive comments:

```cpp
RETURN_IF_ERROR(
    (err != ESP_OK),                                                         // Expression
    TRANSLATE_ERROR(err),                                                    // Error code
    SYS_LOG_E("esp_ota_begin failed: %s (0x%x)", ERROR_MESSAGE(err), err)    // Error message / Log
);
```
