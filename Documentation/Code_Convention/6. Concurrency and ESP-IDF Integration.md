### Concurrency and ESP-IDF Integration

Use this standard to write thread-safe, asynchronous, and RTOS-compliant C++ code within the dual-core FreeRTOS environment of the ESP32.

---

#### 1. Shared Resource Synchronization (FreeRTOS Locks)
When multiple tasks access or modify class member variables (such as arrays, state flags, or socket buffers), you must serialize access using FreeRTOS semaphores or mutexes.

*   **Rule:** For every early-return or error-handling path, ensure that the semaphore or mutex is explicitly released before returning.
*   **Synchronization Template:**
    ```cpp
    sys_error_t HttpsServer::registerUri(IHttpUri& uri)
    {
        // 1. Block until the semaphore becomes available
        if (xSemaphoreTake(_semaphore, portMAX_DELAY) != pdTRUE)
        {
            return ERROR_TIMEOUT;
        }

        // 2. Perform modification inside the critical section
        _registeredUris.push_back(static_cast<HttpUri*>(&uri));

        // 3. Release the semaphore
        xSemaphoreGive(_semaphore);
        return ERROR_SUCCESS;
    }
    ```

---

#### 2. Interrupt Service Routine (ISR) Constraints
Code executed within an ISR context is subject to strict execution time and API limitations to prevent system crashes and watchdog resets.

*   **Rules:**
    *   **No Blocking Operations:** Never use blocking delays (`vTaskDelay`), obtain blocking mutexes, or wait on queues inside an ISR.
    *   **No Allocation/Deallocation:** Do not allocate heap memory (`new`, `malloc`) or release heap memory (`delete`, `free`).
    *   **No Standard Logging:** Never invoke standard logging macros (`SYS_LOG_x` or `printf`) inside an ISR.
    *   **FromISR API Rule:** Only invoke FreeRTOS APIs that explicitly end with the `FromISR` suffix (e.g., `xQueueSendFromISR`, `xSemaphoreGiveFromISR`).
    *   **Context Switch Parameter:** Pass `BaseType_t *pxHigherPriorityTaskWoken` to all `FromISR` APIs to ensure immediate context switching if a higher-priority task is unblocked.

---

#### 3. Multi-Threaded Callbacks and Task Contexts
Callbacks registered to ESP-IDF drivers or protocol stacks (such as HTTP events, Wi-Fi events, or SSL handshakes) run within the context of the underlying SDK task, not your application task.

*   **Rule:** Any application state modified inside a callback must be thread-safe. Use thread-safe queues or atomic variables (`std::atomic`) to pass data from a driver callback back to your application thread.
*   **Callback Context Isolation:**
    ```cpp
    void HttpsServer::https_server_user_callback(esp_https_server_user_cb_arg_t* user_cb)
    {
        // This callback is executed inside the 'httpd' task thread context, NOT the application thread.
        switch (user_cb->user_cb_state)
        {
            case HTTPD_SSL_USER_CB_SESS_CREATE:
                // Modifying any member variable here requires a thread-safe atomic or mutex lock.
                break;
            default:
                break;
        }
    }
    ```

---

#### 4. Task Parameterization
Hardcoding RTOS task priorities and stack sizes can lead to stack overflows or priority inversion.

*   **Rule:** Standardize and expose configuration variables for stack sizes and task priorities in your class initialization structures, allowing them to be tuned based on the application's overall memory map.
*   **Configuration Propagation Template:**
    ```cpp
    sys_error_t HttpsServer::populate_config(const HttpServerStartOptions_t& options, httpd_ssl_config_t& sslConfig)
    {
        // Expose stack and priority options instead of hardcoding values
        sslConfig.httpd.stack_size       = options.task_stack_size;
        sslConfig.httpd.task_priority    = options.task_priority;
        sslConfig.httpd.max_open_sockets = options.max_connections;

        return ERROR_SUCCESS;
    }
    ```
