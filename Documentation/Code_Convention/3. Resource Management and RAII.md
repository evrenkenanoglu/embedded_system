### Resource Management and RAII

Use these guidelines to manage system resources, memory buffers, and synchronization primitives safely in C++ within the ESP-IDF RTOS environment.

---

#### 1. Rule of Five and Resource Ownership
Any C++ class wrapping a physical peripheral, communication link, or driver handle (such as `HttpsClient`, `HttpsServer`, or `mem_ota`) must strictly enforce unique ownership. Copying and moving these classes is prohibited to prevent duplicate deletions and dangling hardware handles.

*   **Destructor Rule:** Destructors must call the corresponding deinitialization or stop routine (e.g., `deInit()`, `stop()`, or `disconnect()`) to ensure graceful resource release when going out of scope.
*   **Disabled Copy/Move Template:**
    ```cpp
    class HttpsServer : public IHttpServer
    {
    public:
        explicit HttpsServer(const HttpServerStartOptions_t& options);
        ~HttpsServer() override;

        // Explicitly block copy mechanics to enforce unique ownership
        HttpsServer(const HttpsServer&) = delete;
        HttpsServer& operator=(const HttpsServer&) = delete;

        // Explicitly block move mechanics unless specifically designed
        HttpsServer(HttpsServer&&) = delete;
        HttpsServer& operator=(HttpsServer&&) = delete;
    };
    ```

---

#### 2. Heap Management and Out-of-Memory (OOM) Handling
Dynamic memory allocation in an embedded context must be deterministic and fully protected against failure.

*   **No-Throw Allocation:** Use `std::nothrow` with the placement-new operator when allocating heap blocks dynamically. This prevents C++ exceptions from firing and allows safe `nullptr` checks.
*   **Smart Pointers:** Wrap heap-allocated buffers in `std::unique_ptr` to automate memory cleanup and prevent leaks.
*   **Heap Allocation Template:**
    ```cpp
    const size_t buf_size = 1024;
    std::unique_ptr<char[]> buf(new (std::nothrow) char[buf_size]());
    if (!buf)
    {
        SYS_LOG_E("Out of memory - Callback execution failed!");
        return; // Safe exit on allocation failure
    }
    // buf is automatically freed when it goes out of scope
    ```

#### 3. Alignment and Strict Aliasing Safety (Memory Serialization)
Directly casting raw byte arrays (e.g., network frames or flash data blocks) to custom structures via `reinterpret_cast` violates strict aliasing rules and can trigger hardware alignment faults (bus errors) on 32-bit Xtensa architectures.

*   **Rule:** Always copy data into a local stack-allocated struct using `std::memcpy`. This ensures the structure is correctly aligned to word boundaries.
*   **Safe Parsing Template:**
    ```cpp
    // AVOID: const esp_app_desc_t* desc = reinterpret_cast<const esp_app_desc_t*>(raw_buffer);

    // PREFERRED: Safe copy to stack
    esp_app_desc_t app_info;
    std::memcpy(&app_info, raw_buffer + offset, sizeof(esp_app_desc_t));
    ```

#### 4. Synchronization Primitives
To prevent lockouts and deadlocks on critical shared resources, manage semaphores and mutexes using scoped RAII locks wherever possible, rather than calling manual release routines on error exit blocks.

*   **FreeRTOS Semaphore Helper Rule:** When direct FreeRTOS API calls are used, ensure that resources are unlocked on every early-exit branch using standard error-macros.
*   **Resource Protection Guard Template:**
    ```cpp
    sys_error_t HttpsServer::registerUri(IHttpUri& uri)
    {
        // Obtain lock before modifying shared vectors
        if (xSemaphoreTake(_semaphore, portMAX_DELAY) != pdTRUE)
        {
            return ERROR_TIMEOUT;
        }

        // Perform protected modifications
        _registeredUris.push_back(static_cast<HttpUri*>(&uri));

        // Always release the lock before returning
        xSemaphoreGive(_semaphore);
        return ERROR_SUCCESS;
    }
    ```
