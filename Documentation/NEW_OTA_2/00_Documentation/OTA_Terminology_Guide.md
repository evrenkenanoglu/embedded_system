## 1. Cryptographic Fundamentals (Asymmetric vs. Symmetric)

| Term                             | Simple Definition                                                                                                                                                                                         | Conceptual Analogy                                                                                          | How it Works in Your System                                                                                                                                                      |
| :------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Asymmetric Cryptography**      | A system that uses a mathematically linked pair of keys: a **Private Key** (kept secret) and a **Public Key** (shared with everyone). What one key locks/encrypts, only the other can unlock/decrypt [2]. | A lockbox with two separate key holes: Key A (Private) can only lock it; Key B (Public) can only unlock it. | Used to verify the identity of the server, authorize developer certificates, and check the signature on the reassembled firmware binary on the ESP32 [2].                        |
| **Symmetric Cryptography**       | A system where the **exact same key** is used to both lock (encrypt) and unlock (decrypt) data. It is highly optimized and fast, but requires a secure way to share the single key first.                 | A standard physical padlock where the same physical key locks and unlocks the box.                          | Used inside the active TLS/SSL connection. Once the asymmetric handshake verifies identities, a temporary symmetric key is generated to encrypt the actual payload transmission. |
| **Cryptographic Hash (SHA-256)** | A mathematical function that converts any input file into a fixed-size **32-byte (256-bit) digital fingerprint**. It is a one-way street: you cannot recreate the file from the fingerprint.              | Taking a physical object and grinding it into a unique, uncopiable paint splatter.                          | The ESP32 calculates a SHA-256 hash of the final written partition up to the exact `target_size` to verify its integrity [2].                                                    |

## 2. Public Key Infrastructure (PKI) & Certificate Hierarchy

| Term                                           | Simple Definition                                                                                                                                                                                          | Conceptual Analogy                                                                                                      | How it Works in Your System                                                                                                                                      |
| :--------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Public Key Infrastructure (PKI)**            | The complete ecosystem of hardware, software, keys, certificates, and policies used to manage trust and secure communications [2].                                                                         | The entire national passport and identity verification system managed by a government.                                  | Governs the creation of Root CAs, the issuance of developer certificates, and how the client validates files.                                                    |
| **Certificate Authority (CA)**                 | A trusted entity that verifies identities and issues digital certificates (ID cards) to servers or developers [2].                                                                                         | The official government agency that reviews birth certificates and issues official passports.                           | The authority that signs your developer certificate to prove you are authorized to push updates.                                                                 |
| **Root CA (`ca.crt`)**                         | The master trust anchor. A self-signed master certificate that represents the ultimate source of truth in a PKI. If a device trusts the Root CA, it automatically trusts any certificate signed by it [2]. | The master database and central seal of the main passport office.                                                       | Pre-installed in the ESP32's flash memory. The ESP32 will immediately reject any file or certificate unless it can trace its signature back to this Root CA [2]. |
| **Digital Certificate (`signing.crt` / Cert)** | A digital ID card that binds a Public Key to a specific identity. It contains the owner's identity, public key, and a signature from the Certificate Authority [2].                                        | An official physical passport containing your photo, your signature, and the government's official watermarked stamp.   | Sent to the ESP32 in the update JSON. It holds your Developer Public Key, proving you own the private `signing.key` used to generate the signature [2].          |
| **Certificate Chain**                          | A sequence of certificates traced back to a trusted Root CA. Each certificate is signed by the certificate above it in the chain [2].                                                                      | A passport containing visas, where each visa's authenticity is verified by tracing back to the master government stamp. | The ESP32 checks `signing.crt` -> verifies it is signed by `ca.crt` -> trusts the developer's public key inside `signing.crt` [2].                               |
| **Trust Anchor**                               | A public key or certificate that is hardcoded or securely pre-installed on a system that forms the absolute basis of trust.                                                                                | The physical blueprint of the government's master stamp given to airport border guards.                                 | The `ca.crt` file compiled directly into your ESP32 application build.                                                                                           |
| **Key Delegation**                             | Trusting a master key to safely sign and authorize a secondary key to perform actions.                                                                                                                     | A president signing an executive order to authorize a specific general to sign treaties.                                | The Root CA signs your `signing.crt` so you can sign firmware binaries without exposing the master Root CA private key (`ca.key`) [2].                           |

## 3. Signing, Verification & Abstractions

| Term                         | Simple Definition                                                                                                                       | How it Works in Your System                                                                                                                             |
| :--------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Code Signing / Signing**   | The process of generating a cryptographic signature on a file by hashing it and encrypting the hash with a Private Key [2].             | The server hashes your compiled `.bin`, encrypts that hash with `signing.key`, and creates the `target_signature` metadata [2].                         |
| **Digital Signature / Seal** | The actual encrypted hash appended to a file. It acts as an uncopiable, tamper-evident seal [2].                                        | Included in the server's update JSON. If a hacker alters even a single byte of the firmware, the computed hash will not match the decrypted signature.  |
| **Signature Verification**   | Mathematically confirming a signature is valid using the corresponding Public Key and recalculating the local hash [2].                 | The ESP32 hashes the reassembled binary in flash and uses the public key from `signing.crt` to verify `target_signature` via `mbedtls_pk_verify` [2].   |
| **mbedTLS**                  | A lightweight, open-source C library that provides cryptographic primitives, SSL/TLS, and certificate parsing for embedded systems [2]. | The underlying software engine running on the ESP32 that calculates SHA-256 hashes, parses x509 certificates, and executes signature verifications [2]. |

## 4. OTA Transport & Mechanics

| Term                                  | Simple Definition                                                                                                                  | How it Works in Your System                                                                                                                                 |
| :------------------------------------ | :--------------------------------------------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Over-the-Air (OTA)**                | Updating device software remotely over a wireless connection.                                                                      | The ESP32 smart plug regularly connects to the server to check for, download, and apply updates.                                                            |
| **Presigned Token / Transient Token** | A cryptographically signed query parameter appended to a URL that grants temporary access to a file (e.g., valid for 300 seconds). | The server calculates a time-limited HMAC-SHA256 token and appends `?token=...` to the download URL to restrict direct, permanent file access.              |
| **A/B Dual-Bank Partitioning**        | Dividing the device's storage into two identical application slots (Active and Staging) to prevent bricking if an update fails.    | The ESP32 runs from Partition A while writing the incoming update into Partition B. If the stream cuts, Partition A remains intact.                         |
| **Delta Update / Patch**              | Transmitting only the binary *differences* between the old and new software versions to save network data.                         | The server uses `detools` to generate a patch. The ESP32 uses `esp_delta_ota` to decompress and apply the patch using its active partition as a dictionary. |
| **Full Update**                       | Transmitting the entire, monolithic firmware binary file to the device.                                                            | Delivered by the server as a fallback when no pre-generated delta patch is available for the client's current version.                                      |

## 5. Fleet Orchestration & Guardrails

| Term                     | Simple Definition                                                                                                                 | How it Works in Your System                                                                                                                               |
| :----------------------- | :-------------------------------------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Release Channels**     | Segmented deployment streams used to target different populations of devices (e.g., `stable`, `beta`, `testing`, `development`).  | Test smart plugs are assigned the `development` channel to safely verify test builds without updating production customer devices.                        |
| **Anti-Rollback (HSVN)** | A hardware security block that prevents older, vulnerable firmware versions from being installed by checking a monotonic counter. | The ESP32 reports its Hardware Security Version Number. The server blocks the update if the target firmware's HSVN is lower than the client's.            |
| **Canary Rollout**       | Gradually deploying an update to a tiny percentage of devices (e.g., 10%) first to check for stability before updating everyone.  | The server runs an MD5 calculation on the device ID and latest version to deterministically assign the device to a rollout group.                         |
| **Telemetry Loop**       | Devices sending structured success or failure reports back to the server after attempting an OTA update.                          | The ESP32 calls `/api/v1/ota/status` to log success, failure, and platform-specific error codes (e.g., signature verify failed).                          |
| **Soft Rollback**        | An automated safety net that stops an update on the server if too many devices report failures.                                   | The server monitors `/status` logs. If the failure rate of a version exceeds the allowed limit (e.g., 10%), the server deactivates it in `manifest.json`. |
